# imot2026 stack on vm700

Deploys the imotbgScraper2026 real-estate ingestion platform (MongoDB, Kafka,
and nine `imot2026-app` services sharing one image) on vm700 (192.168.31.152),
managed by `roles/ops-settings/tasks/imot2026.yaml`.

Deploy is `make ops` from `ansible-home-lab`, tag `imot2026_stack`. Nothing
here is applied automatically — see **Enablement** below.

---

## 1. Why this shape, and where it disagrees with the sibling repo

This ports `imotbgScraper2026/deploy/deploy.yaml` (a standalone playbook that
already deploys this stack, ad hoc, from that repo) into the ansible-home-lab
house pattern, the same way `caddy.yaml`'s header describes porting a
standalone compose project into this role. Three things carry over
unconditionally: the stack lives under `/opt/imot2026`, mongo's data lives
under `/var/lib/docker-data/imot2026-mongo`, and the image is **built on
vm700**, never pulled — there is nowhere to pull it from yet, and the laptop
is arm64 while vm700 is amd64 (imotbgScraper2026's own
`docs/spec/deployment.md` §3).

One thing does **not** carry over: **the compose file and `.env` are not
re-authored in this repo.** `caddy.yaml` authors its own Caddyfile templates
because Caddy's routing config is inherently ops/infra configuration with no
other home. imot2026's `docker-compose.yml.j2` and `env.j2` are different —
they define the **application's own services**, and imotbgScraper2026 already
owns and maintains them. Keeping a second, hand-copied version here is
precisely the failure mode `docker-compose.yml.j2` warns about in its own
header comment: *"Never edit the rendered file by hand; edit this template
and re-run the playbook"* — and imotbgScraper2026's own `scripts/preflight.sh`
exists to catch exactly this kind of drift between a copy and its source.
Keeping a second copy in ansible-home-lab is the drift that check cannot see.

The closer precedent already in this role is `omniroute.yaml`: OmniRoute's
`docker-compose.prod.yml` is owned by the upstream OmniRoute project, and
`omniroute.yaml` checks it out and applies it via the compose `files:` list
rather than re-authoring it — ops-settings supplies only its own
`docker-compose.override.yml.j2` and `.env.j2`. `imot2026.yaml` follows the
same principle: it renders `imotbgScraper2026/deploy/docker-compose.yml.j2`
and `env.j2` **directly from the sibling checkout**
(`imot2026_repo_dir: "{{ playbook_dir }}/../imotbgScraper2026"`, the same
sibling-checkout assumption `imotbgScraper2026/deploy/deploy.yaml` itself
makes about `../ansible-home-lab`), using Ansible's `template:` module —
`template:`'s `src` is always read on the controller regardless of which host
the task targets, the same way it reads a role's own `templates/` directory,
so this needs no extra fetch step. This was verified directly while writing
this role: both files render and, for the compose file, parse as valid YAML
with every Jinja variable they reference supplied (`imot2026_git_sha`,
`imot2026_library_host_path`, `imot2026_mongo_host_port`,
`imot2026_web_host_port` (named `imot2026_ops_api_host_port` here until 2026-08-23,
when this repo caught up with imotbgScraper2026's ops-api→web rename) — nothing else; confirmed with
`jinja2.StrictUndefined`).

Two further disagreements, both resolved in favor of this repo's own
conventions over the sibling playbook:

| topic | `imotbgScraper2026/deploy/deploy.yaml` | this role |
|---|---|---|
| `/opt/imot2026` ownership | `become: true` on the file task only, `owner: "{{ ansible_user_id }}"` — because the play itself runs `become: false` (docker group membership is enough for the rest of that playbook) | `become: true` explicit on the directory tasks, `owner: root` / `group: root` — matching `caddy.yaml`'s and `omniroute.yaml`'s directories, because the containing play (`playbook-index.yaml`, `hosts: ops`) already runs `become: true` throughout, so every rendered file in this role is root-owned already |
| free-space / mount preconditions | present, correct, host-only (no `delegate_to`) | reproduced here with the same reasoning (containerd snapshotter, not `df /`; `mountpoint`, not `-d`), because this role's own preconditions must hold independently of whichever playbook happens to run first |

Both playbooks now do the become/owner and precondition checks correctly —
an earlier version of this task's brief warned that the sibling playbook
"only works because its directory already exists from an earlier
out-of-band creation." That is no longer true of
`imotbgScraper2026/deploy/deploy.yaml` as of 2026-08-22 (it creates
`/opt/imot2026` itself, with `become: true` and an explicit owner). It is
noted here so a future reader does not have to rediscover it: **do not
assume `/opt/imot2026` pre-exists in either playbook.**

This does leave two independent ways to deploy the same stack (the sibling
repo's own `deploy/deploy.yaml`, and this role's `imot2026.yaml`) until one
is retired. That overlap is a known, deliberate trade-off of this port, not
an oversight — see §11.

## 2. Image — built on vm700, never pulled

There is no published `imot2026-app` image; one does not exist on any
registry today. `imot2026.yaml`:

1. Syncs the imotbgScraper2026 working tree to `/opt/imot2026/src-tree` on
   vm700 (`ansible.posix.synchronize`, excluding `.git`, `node_modules`,
   `coverage`, `work`, and `protected`).
2. Builds `imot2026-app:{{ imot2026_git_sha }}` there with
   `community.docker.docker_image_build`, `dockerfile: Dockerfile`,
   `args: {GIT_SHA: ...}`.
3. Starts the stack with `community.docker.docker_compose_v2`,
   **`build: never`** — compose only ever runs what was already built above.

`build: never` on the compose step is the same house rule `caddy.yaml` and
`omniroute.yaml` follow, for the same reason: an unbounded
`docker compose build` on this host once peaked at 13.4 GB RSS and
OOM-killed RocketChat, LiteLLM and music-production-engine (documented in
`omniroute.yaml`'s header). The difference here is that *something* still has
to build the image — imot2026 has no upstream to pull from — so the build
happens once, explicitly, via `docker_image_build`, guarded by the disk-space
preconditions in §4, rather than letting compose decide when and how to
build.

`imot2026_git_sha` is read on the **controller** with
`lookup('pipe', 'git -C ' + imot2026_repo_dir + ' rev-parse HEAD')`, and a
companion `git status --porcelain` check refuses to build a dirty tree — the
same rule `imotbgScraper2026/deploy/deploy.yaml` enforces, for the same
reason: the image is synced from the working tree but tagged with the
committed SHA, so a dirty tree would ship code the tag does not describe.

## 3. Paths

| what | where |
|---|---|
| stack dir | `/opt/imot2026` (root:root 0755) |
| rendered compose + env | `/opt/imot2026/docker-compose.yml`, `/opt/imot2026/.env` |
| synced source for the build | `/opt/imot2026/src-tree` |
| mongo data | `/var/lib/docker-data/imot2026-mongo` (root:root 0755, bind-mounted into the container — the exact host path is pinned in `docker-compose.yml.j2` itself, not passed in) |
| local media cache | `imot2026_media_cache_host_path`, default `/var/lib/docker-data/imot2026-media-cache` (owner 10001:10001 0750) — on `/dev/sdb`, migrated off `/dev/sda2` root disk |
| NAS-backed library | `imot2026_library_host_path`, default `/mnt/nas/imot2026` — **not mounted by this role**, see §10 |

`/opt` is root:root 0755 on vm700 (verified 2026-08-22) — every directory
this role creates under it is created with `become: true` and an explicit
`owner: root`, never assumed to pre-exist.

## 4. Preconditions asserted on vm700

All host-only, no `delegate_to`, so they run against vm700 itself:

* **Image-layer free space, on the right filesystem.** Docker 29's containerd
  snapshotter puts image layers under `/var/lib/containerd`, not `/`.
  Verified live on vm700, 2026-08-22: `/var/lib/containerd` is `/dev/sdb`
  (196G total, ~100G free); `/` is `/dev/sda2` (79G total, ~64G free) — two
  genuinely different disks. `df /` would silently check the wrong one.
  Threshold: `imot2026_min_image_store_free_gb` (default 15).
* **Root filesystem headroom.** `/` still holds logs, apt state, and (until
  the mongo bind mount exists) the parent of `/var/lib/docker-data`.
  Threshold: `imot2026_min_root_free_gb` (default 5).
* **Free space where mongo's data will be written.**
  Threshold: `imot2026_min_mongo_free_gb` (default 5).
* **The NAS library path is a real mount, not an empty directory standing in
  for one.** `mountpoint <path>`, asserted before compose ever starts (every
  `imot2026-*` service bind-mounts this path at `/library`). See §10 — this
  role does not create the mount itself.
* **The imotbgScraper2026 working tree is clean.** See §2.

A `docker image prune -af --filter "until=24h" && docker builder prune -af`
runs before the free-space check, on the same reasoning as the checks
themselves: reclaim what nothing references before deciding whether there is
room for a new build.

## 5. Health gate

After `docker_compose_v2` brings the stack up:

1. Wait for `imot2026-mongo`'s Docker healthcheck to report `healthy`
   (`db.adminCommand({ping:1}).ok`, per `docker-compose.yml.j2`).
2. Initiate the replica set once (`rs.initiate(...)`, idempotent — an error
   on an already-initiated set is the success case on every run after the
   first). This is required, not optional: `IMOT2026_MONGO_URI` in the
   compose file hardcodes `replicaSet=rs0&directConnection=true`.
3. Wait for `imot2026-kafka`'s Docker healthcheck to report `healthy`
   (`kafka-broker-api-versions.sh`, per `docker-compose.yml.j2`).
4. `docker compose -p imot2026 ps --format json` to confirm every service in
   the project is running.

**What this gate does not, and cannot yet, prove:** there is no `/health`
endpoint to assert a version against. `src/cli.ts` in imotbgScraper2026
implements exactly one subcommand (`scan`) as of 2026-08-22
(`docs/spec/implementation-plan.md` slices 8-12 are pending). Every service
but mongo and kafka — scanner, indexer, reviewer, projector, notifier,
email-worker, discord-worker, media-worker, ops-api — will start, print
`src/cli.ts`'s usage error, and exit non-zero. `restart: unless-stopped`
means Docker keeps retrying it. That is the compose file's own documented
behaviour, not a defect in this role, and it is why `imot2026_enabled`
defaults to `false` (§11) rather than being safe to leave on.

## 6. Secrets — Discord and email routing

`env.j2` (rendered from imotbgScraper2026's own template, §1) reads
`imot2026_discord.webhook_url` / `.bot_token` and `imot2026_email.provider` /
`.api_key` / `.from_address` / `.from_name`. imotbgScraper2026's own
`deploy.yaml` sources these from its own `protected/config/discord.yaml` and
`protected/config/accounts/email.yaml` — **a different repo's `protected/`
tree, never read from this one.**

Instead, `imot2026.yaml` builds those two dicts from flat
`imot2026_discord_webhook_url`, `imot2026_discord_bot_token`,
`imot2026_email_provider`, `imot2026_email_api_key`,
`imot2026_email_from_address`, `imot2026_email_from_name` defaults (all empty
strings except `from_name`). Real values belong in
`ansible-home-lab/protected/inventories/group_vars/all.yaml`, referenced by
name only — this repo is public (`AGENTS.md`). Left empty, the corresponding
worker starts but cannot publish or send, matching imotbgScraper2026's own
documented behaviour for a missing config file.

## 8. Idempotence

`docker_compose_v2` with `state: present` reconciles the running stack
against the freshly rendered `docker-compose.yml` on every run — a changed
image tag (new `imot2026_git_sha`) or a changed rendered file both trigger a
recreate; an unchanged run reports `changed: false` for the compose task
itself. The replica-set initiation task is deliberately `changed_when: false`
always — it either performs a one-time action or hits the documented "already
initiated" error, and neither is a meaningful state change to report.

## 9. Rollback

There is no automated rollback task — this mirrors caddy.yaml, which also
has none, rather than inventing a new mechanism. To roll back by hand:

1. `docker compose -p imot2026 down` on vm700 stops the stack without
   touching `/var/lib/docker-data/imot2026-mongo` (mongo's data survives).
2. Re-run the role with a previous `imotbgScraper2026` commit checked out
   (`git -C imotbgScraper2026 checkout <sha>`) to rebuild and redeploy that
   version — the dirty-tree check in §2 means the checkout must be clean.
3. If the replica set was initiated against data that needs discarding
   entirely, remove `/var/lib/docker-data/imot2026-mongo` (as root) before
   the next run — this is destructive and irreversible; take a copy first
   if the data has any value.

Kafka's topic data lives in the named volume `imot2026-kafka-data`, not on a
host bind mount; `docker compose down` without `-v` leaves it intact,
`docker compose down -v` (not run by this role) would discard it.

## 10. What is deliberately not automated

* **The NAS mount itself.** This role asserts `imot2026_library_host_path`
  is a real mount point (§4) but does not create it — the export's
  host/path/options live in imotbgScraper2026's own
  `protected/config/nfs.yaml`, a different repo's secret tree, and per
  "One Tool Per Layer" (`AGENTS.md`) host/mount state belongs to Ansible in
  *this* repo, not to values read out of another repo's `protected/`. As of
  2026-08-22 nothing is mounted at `/mnt/nas/imot2026` on vm700 (verified —
  only `/mnt/nas/mpe` and `/srv/mpe-library` exist there today, both for
  music-production-engine). Until this is resolved, enabling
  `imot2026_enabled` will fail at the mountpoint assertion, by design: a
  loud failure here is preferable to nine services silently bind-mounting
  local disk in place of the NAS export.
* **uid 10001 write probe.** `imotbgScraper2026/deploy/deploy.yaml` proves
  the NFS export doesn't squash the container's uid by writing a file as
  that uid and reading its owner back. Not reproduced here, because it is
  meaningless until the mount above exists; add it alongside whichever role
  ends up owning the mount.
* **`scripts/verify_vm700.sh`.** Not extended with ports 27019/8790 in this
  change — `caddy.yaml`'s equivalent doc (`caddy.md` §12) calls this out
  explicitly when it *is* done; this stack is not enabled by default and
  isn't part of the steady-state port sweep yet.
* **Retiring `imotbgScraper2026/deploy/deploy.yaml`.** Both deploy paths
  exist side by side for now (§1). Deciding which one is canonical, and
  removing the other, is a follow-up, not part of this port.
* **A real health check.** See §5 — there is nothing to check yet.

## 11. Enablement and blast radius

`imot2026_enabled` defaults to **`false`**. Unlike `caddy_enabled` (gated
because it binds host `:80`/`:443` on a live box), `imot2026_enabled` is
gated because:

* the nine `imot2026-app` services are not functional yet (§5) — enabling
  this today deploys a stack that mostly restart-loops, which is confusing
  noise on `docker ps` for no operational benefit;
* every enabled run does a full image **build** on vm700, which is exactly
  the class of operation that has OOM-killed this host before (§2, §4) —
  it should never happen as a side effect of an unrelated `make ops`;
* the NAS mount precondition (§10) is not currently satisfied on vm700, so
  enabling it today fails loudly rather than deploying successfully — that
  is intentional, but still not something a routine `make ops` should
  attempt by accident.

Turn it on deliberately:

```sh
ansible-playbook -i protected/inventories/inventory-main.yaml playbook-index.yaml \
  -l ops --tags imot2026_stack -e imot2026_enabled=true
```

Nothing in this file has been run against vm700. This role is
authoring-only as written — see the task's own eval
(`evals/020-main-core--imot2026-stack.json`) for exactly what was and was not
validated.
